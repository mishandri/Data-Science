# JPX Tokyo Stock Exchange Prediction

Итоговый проект по Kaggle-соревнованию **[JPX Tokyo Stock Exchange Prediction](https://www.kaggle.com/competitions/jpx-tokyo-stock-exchange-prediction)** —
прогноз ранжирования акций японского рынка и построение инвестиционного портфеля.

**Задача.** Каждый торговый день нужно ранжировать ~2000 акций по ожидаемой доходности
(0 — самая перспективная). Оценка — **Sharpe Ratio** дневной доходности «длинно-короткой»
стратегии: покупаем 200 акций с лучшим рангом, продаём в шорт 200 с худшим.

**Особенность соревнования.** Это *code competition*: данные тестового периода приходят
по одному торговому дню через time-series API, а файл `submission.csv` создаёт сам API.
Именно поэтому ноутбук не пишет `submission.csv` вручную — см. раздел 10 ноутбука
(«Генерация `submission.csv` через официальный time-series API»).

**Отправка результата.** Соревнование закрыто, новые отправки не принимаются. Свою
отправку я сделал уже после окончания соревнования, поэтому в этом readme нет ни одной
цифры с лидерборда: все оценки ниже сняты с локальной walk-forward валидации. Данные и
time-series API при этом доступны, так что ноутбук воспроизводится, а инструкция по
отправке ниже остаётся рабочей.

## Как запустить

```bash
pip install -r requirements.txt

```

Данные нужно положить рядом с ноутбуком (или на уровень выше — путь ищется автоматически):

```
<папка проекта>/
├── jpx_tokyo_market_prediction.ipynb
├── train_files/stock_prices.csv
├── supplemental_files/stock_prices.csv
├── example_test_files/…
└── …
```

Куда именно класть файлы и как их скачать — в [`data/README.md`](data/README.md).
Важно: поиск идёт по `.`, `..` и `../..`, поэтому **положить данные в подпапку `data/`
нельзя** — ноутбук её не увидит и упадёт с `FileNotFoundError`.

Ноутбук сам находит каталог с данными (`find_data_dir()`): пробует `.`, `..`, `../..`,
а на Kaggle рекурсивно ищет папку с `train_files/stock_prices.csv` во всём `/kaggle/input`
(имя каталога может быть любым — `jpx-tokyo-stock-exchange-prediction`, `-1`, `-2` и т.п.).
Если данные не прикреплены, ноутбук падает с понятной подсказкой, что именно нужно добавить.

**Локально** официальный API соревнования недоступен (это скомпилированный linux-модуль),
поэтому включается `local_iter_test()` — имитация API на файлах `example_test_files`.
Ноутбук отрабатывает полностью и пишет `local_submission.csv` **для проверки**.

Полный прогон на CPU — примерно 4 минуты на 2.6 млн строк.

## Как получить оценку на Kaggle

Соревнование уже закрыто, поэтому новой отправки не будет. Раздел остаётся потому, что
без него непонятно, почему в ноутбуке нет `to_csv('submission.csv')` и почему локальный
прогон пишет `local_submission.csv`: эти требования приходят от API, а не от вкуса.

### Важно: ноутбук должен работать на Python 3.7

Пакет `jpx_tokyo_market_prediction` (time-series API, который и создаёт `submission.csv`)
скомпилирован под **CPython 3.7** — файл `competition.cpython-37m-x86_64-linux-gnu.so`.
По умолчанию Kaggle выполняет ноутбуки на **Python 3.13**, где этот файл не находится:

```
Python: 3.13.15
Официальный API доступен: False
Ошибка импорта API: ModuleNotFoundError: No module named 'jpx_tokyo_market_prediction.competition'
```

Расширение Python подгружается только при совпадении ABI-тега, поэтому переименовать файл
или подсунуть его вручную нельзя — модуль собран против внутренностей CPython 3.7.

### Порядок действий

**на котором он сам был создан**, а не к образу 2022 года.

Рабочий путь — начать с ноутбука, созданного **в 2022 году**, когда Python 3.7 был
актуальным. В соревновании есть такой публичный ноутбук с работающим счётом:

### Совместимость с Python 3.7

Ноутбук рассчитан на окружение соревнования (Python 3.7, pandas 1.3, matplotlib 3.5):

* имя стиля matplotlib подбирается из нескольких вариантов с проверкой;
* параметр `boxplot(vert=...)` обёрнут в `try/except` (в новых версиях он переименован);
* `HistGradientBoostingRegressor` импортируется с проверкой, при неудаче используется
  `GradientBoostingRegressor`, а при отсутствии LightGBM — permutation importance;
* импорт `importance_type='gain'` у LightGBM имеет запасной вариант.

### Если Kaggle показывает ошибку перезапуска

При отправке Kaggle **сам перезапускает ноутбук на скрытых данных** и показывает только
класс ошибки, а не traceback. Что означают эти сообщения и где смотреть подробности:

| Класс ошибки               | Что это                                                                   | Где смотреть детали                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `Submission CSV Not Found`          | ноутбук отработал, но`submission.csv` не появился | вкладка**Output** у версии ноутбука, с которой отправляли |
| `Notebook Threw Exception`          | на скрытых данных упала ячейка                        | **Logs** этой версии + **Output**                                                 |
| `Submission Scoring / Format Error` | файл создан, но неверного формата                   | сами ranks: плотные`0..N-1`, без дублей                                           |
| `Notebook Timeout`                  | не уложился в лимит времени                              | Code Requirements соревнования (9 часов)                                               |
| `Notebook Exceeded Allowed Compute` | запросил больше RAM/диска, чем доступно           | Logs                                                                                                    |

Ноутбук к этому подготовлен:

* размеры обучающих и валидационных окон **подстраиваются** под реальное число дней
  в данных, поэтому скрытый датасет другого размера не сломает валидацию;
* обучающая история срезается до последних 1500 торговых дней (`MAX_TRAIN_DAYS`), а в
  цикл API уходит только хвост из 150 наблюдений на бумагу (`HISTORY_DAYS`) — этого
  хватает для всех окон, самое длинное из них 60 дней, и память предсказуема на любом
  объёме данных;
* дни, где бумаг меньше двух портфелей, пропускаются в метрике, а не роняют расчёт;
* **каждый тестовый день обрабатывается в своём `try/except`**: если на конкретной
  итерации что-то пошло не так, ноутбук подставит нейтральный порядок и всё равно
  доведёт отправку до конца, а в лог напишет `[ВНИМАНИЕ] День ... обработан запасным сценарием`. Это ровно тот совет из справки Kaggle — «fail gracefully and still
  produce a score»;
* в финальном отчёте печатается `Дней с запасным сценарием: N` — если это не 0,
  стоит посмотреть лог версии.

Что происходит при этом: пакет `jpx_tokyo_market_prediction` становится доступен,
в разделе 10 включается настоящий time-series API, и **`submission.csv` формирует сам API**
из вызовов `env.predict(...)` внутри цикла `env.iter_test()`.

> ⚠️ **Не вызывайте `to_csv('submission.csv')`.** Kaggle закрывает этот путь, и ноутбук
> упадёт с `PermissionError: [Errno 1] Operation not permitted: 'submission.csv'`.
> Локально такая ошибка не воспроизводится — поэтому её легко пропустить.

## Подход к решению

### Данные

| Файл                                | Строк          | Период                            |
| --------------------------------------- | ------------------- | --------------------------------------- |
| `train_files/stock_prices.csv`        | 2 332 531           | 2017-01-04 — 2021-12-03 (1202 дня)  |
| `supplemental_files/stock_prices.csv` | 269 881             | 2021-12-06 — 2022-06-24 (135 дней) |
| **Итого**                    | **2 602 412** | 1337 дней, 2000 бумаг          |

### Признаки (23 штуки)

Считаются функцией `add_features` **внутри каждой акции** (`groupby('SecuritiesCode')`):

* **доходности и лаги** — `ret_1/5/20/60`, гэп между открытием и предыдущим закрытием;
* **волатильность** — скользящие std доходностей (20/60), z-score логарифма объёма;
* **положение цены относительно SMA/EMA** (20/60);
* **свечной паттерн** — тело, диапазон, верхняя и нижняя тени;
* **рыночные (кросс-секционные)** — средняя доходность дня, избыточная доходность,
  ранг бумаги внутри дня;
* **календарь и флаги** — день недели, месяц, наличие дивиденда, флаг наблюдения.

Ни один признак не использует данные из будущего: для дня `t` доступны данные строго
до конца дня `t`.

### Модели

| Модель                                | Роль                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `Ridge` (StandardScaler + гребень) | линейный бейзлайн — сколько даёт сама фактура признаков |
| `LightGBM`                                | градиентный бустинг, основная рабочая модель                     |
| `Blend`                                   | среднее ранговых процентилей Ridge и LightGBM внутри дня            |

### Валидация

**Walk-forward по времени**: 4 фолда × 20 дней, обучение на 400 предшествующих дней,
тест — на следующих 20. Случайное перемешивание не используется: оно завышает оценку
и незаметно пропускает утечку «из будущего в прошлое».

Оценка считается **официальной метрикой соревнования** — Sharpe дневных спредов
top-200 / bottom-200, а не MSE: MSE почти не зависит от ранга и плохо отражает то,
что реально оценивает Kaggle.

## Результаты

Walk-forward валидация, 80 дней (последние 4 месяца доступной истории):

| Модель    | Sharpe          | Средний спред | Ст. откл. спреда | Средний IC | p-value (IC) | p-value (спреда) |
| --------------- | --------------- | ------------------------- | ---------------------------- | ----------------- | ------------ | ---------------------- |
| **Blend** | **0.272** | 0.00598                   | 2.199                        | +0.0385           | 0.014        | 0.017                  |
| LightGBM        | 0.169           | 0.00493                   | 2.921                        | +0.0435           | 0.036        | 0.135                  |
| Ridge           | 0.085           | 0.00190                   | 2.222                        | +0.0147           | 0.304        | 0.447                  |

Спред и его отклонение даны в единицах официальной метрики — это сумма доходностей по
200 акциям, то есть в 200 раз больше доходности самого портфеля. На Sharpe это не влияет.

По фолдам (Sharpe): LightGBM — 0.361 / 0.321 / −0.033 / −0.004, Ridge — 0.109 / 0.110 /
0.134 / −0.155. Разброс по фолдам большой: рыночные эффекты в этом периоде нестабильны,
и это честный результат, а не артефакт валидации.

**Статистические проверки** (уровень значимости 0.05):

* H₀: средняя дневная спред-доходность = 0 → t-тест и тест Уилкоксона;
* H₀: средний ежедневный ранговый IC (Spearman) = 0 → t-тест по IC;
* попарное сравнение моделей → связанный t-тест (`ttest_rel`) на дневных спредах.

Blend и LightGBM дают положительную доходность, Ridge — нет, но по значимости картина
неодинаковая, и это важнее самих Шарпов (уровень 0.05):

* **Blend** — значим по обоим тестам: спред p = 0.017, IC p = 0.014;
* **LightGBM** — значим только ранговый IC (p = 0.036), а средний спред нет (p = 0.135),
  то есть на этих 80 днях его доходность от шума не отличить;
* **Ridge** — не значим ни по одному (p = 0.447 и 0.304).

Финальная модель выбирается автоматически по лучшему CV-Шарпу, и на этой истории это
Blend. Стоит оговорить: настоящий аргумент «за Blend против LightGBM» — это попарный
связанный t-тест, а его результат в этот readme я не перенёс, хотя в ноутбуке он
считается и печатается.

## Ограничения

Свои слабые места я здесь вижу, и часть из них — из-за формата соревнования, а не из-за
принципа «недостаточно хорошая модель».

* **Ноутбук лежит в репозитории без вывода ячеек.** Все числа этого readme — Шарпы,
  важности, тайминги — сняты с отдельного прогона, сверить их прямо здесь нечем:
  нужно положить данные и отработать ноутбук заново.
* **Валидация — это 80 дней из 1337.** Разброс по фолдам такой, что LightGBM то в плюс,
  то в минус (0.361 / 0.321 / −0.033 / −0.004). На таком отрезке модели можно
  ранжировать, но объявлять победителя рано: разница между Blend и LightGBM внутри
  шума.
* **Модель обучается один раз и больше не переобучается.** Финальный предиктор
  фиксируется на последних 600 днях перед стартом цикла API. Это экономит время
  (бустинг на каждом тестовом дне считать дорого) и соответствует правилам соревнования,
  но на длинном тестовом периоде модель устаревает вслед за рынком.
* **Используются только цены и объёмы.** API на каждой итерации отдаёт ещё
  `options.csv`, `financials.csv`, `trades.csv` и `secondary_stock_prices.csv`, и
  ноутбук их игнорирует. Отрасль из `stock_list.csv` не участвует вообще, хотя для
  кросс-секционного ранжирования она обычно полезнее календарных признаков, которые
  здесь оказались на втором-третьем месте по важности.
* **Выбросы подрезаются константами, а не по валидации.** Пороги в `ratio_clip` заданы
  руками и одинаковы для всех бумаг; на узких акциях и на бумагах с дроблением они
  бьют по-разному.
* **Целевая переменная сырая.** Ни отрасль, ни ликвидность, ни размер компании из
  предсказания не вычитаются, поэтому модель может получать доходность не от своей идеи
  бумаги, а от общего движения её группы.
* **Оценка на Kaggle не проверялась.** Отправка была сделана после окончания
  соревнования, метрика с лидерборда не получена. Все числа выше — локальная
  walk-forward валидация по официальной формуле, и перенос её на реальный
  скрытый период — это допущение, а не факт.
